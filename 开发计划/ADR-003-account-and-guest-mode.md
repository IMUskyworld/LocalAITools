# ADR-003：游客模式与账号模式并存，账号不等于远程控制授权

- 状态：已接受
- 日期：2026-09-11
- 决策范围：LocalMind（Windows）、LocalFile（Android）与 LocalMind Relay（公网服务）
- 依赖决策：ADR-002 Relay-first

## 1. 背景

产品需要同时满足两种用户：

1. 只想使用本地 AI、文件处理和 Agent 能力的用户，不应该被强制注册账号。
2. 需要使用双端协同的用户，需要在 Windows 和 Android 登录同一个账号，并通过手机控制已授权电脑。

用户提出的目标是：

> 如果不需要双端协同，就走游客登录，不需要密码；如果需要协同，例如电脑端注册登录一个账号，手机端也登录同一个账号，二者账号是同一个账号，从而通过手机端授权操控电脑端。

该需求成立，但必须区分两个概念：

- **账号身份**：证明两台设备属于同一个用户。
- **远程控制授权**：允许某一个控制设备向某一个目标设备发送受控任务。

仅有“同一个账号”不能自动等于“任意设备都可以控制其他设备”。同一账号下的设备列表可以帮助发现设备，但控制关系仍必须由目标设备本机确认。

## 2. 同类项目调研

调研日期：2026-09-11，检查 GitHub 公开仓库的维护状态和产品模式。

| 项目 | 活跃度观察 | 可借鉴的模式 | 对本项目的启示 |
|---|---|---|---|
| [Tailscale](https://github.com/tailscale/tailscale) | 约 36k stars，持续维护 | 账号身份、设备登记、设备授权、ACL | 账号负责身份，设备仍需登记和授权，不能只靠账号自动互信 |
| [Syncthing](https://github.com/syncthing/syncthing) | 约 88k stars，持续维护 | 设备 ID、显式设备配对 | 设备级配对适合控制类高风险能力 |
| [LocalSend](https://github.com/localsend/localsend) | 约 90k stars，持续维护 | 本地发现、低摩擦传输 | 本地/游客路径应尽量无账号、无配置 |
| [PairDrop](https://github.com/schlagmichdoch/PairDrop) | 约 11k stars，持续维护 | 一次性配对码、无需注册 | 临时配对适合低风险演示，不适合长期远程控制 |
| [ntfy](https://github.com/binwiederhier/ntfy) | 约 34k stars，持续维护 | 公网中继、设备订阅、轻量部署 | Relay 适合做身份路由和状态传递，不应升级为命令执行器 |

结论：

- 游客模式应该保留本地即用，不能因为增加账号系统破坏“下载安装即可使用”。
- 账号系统负责用户身份、设备登记和设备列表。
- 远程控制必须增加设备配对、目标侧确认、权限范围、撤销和审计。
- 端到端加密仍由后续阶段补齐；Relay 继续只处理受认证的版本化 Envelope。

## 3. 方案比较

### A. 只保留游客模式

优点：

- 最低摩擦；
- 不需要账号服务器、密码和找回流程。

缺点：

- 无法稳定识别“我的设备”；
- 跨端协同只能依赖临时配对码；
- 无法做账号级设备撤销、用户维度的审计和多设备管理。

否决作为唯一方案，但保留为游客模式。

### B. 账号登录后，同账号设备自动互信

优点：

- 用户体验简单；
- 只要两端登录同一账号即可看到设备。

缺点：

- 任意登录同一账号的设备获得过大权限；
- 一旦账号被盗或用户在公共设备误登录，控制面风险过高；
- 无法表达“只允许某台手机控制某台电脑”。

否决。

### C. 游客模式 + 账号身份 + 设备显式授权（采用）

优点：

- 游客仍可本地使用；
- 账号负责设备归属和发现；
- 目标设备必须本机确认才能建立控制关系；
- 可以按设备、按权限范围撤销；
- 适合后续加入端到端加密、审计和多设备管理。

代价：

- 比“同账号自动互信”多一步授权操作；
- 需要新增账号数据表、认证接口、令牌轮换和设备管理 UI。

决定采用 C。

### D. 接入第三方 OAuth/SSO

优点是复用成熟身份系统，但当前是校级演示项目，外部身份服务、备案和运维依赖会扩大当前范围。保留为未来扩展，不作为 Phase 2 前置。

## 4. 产品规则

### 4.1 游客模式

- 无需账号、无需密码。
- 本地 AI 对话、本地文件处理、本地文档生成和本地 Agent 正常可用。
- 远程设备列表、配对、跨端任务和账号同步入口默认禁用。
- 点击协同功能时提示“登录后使用”，不能静默失败。
- 游客升级账号时保留本地数据；默认不上传本地会话、文件内容和工具结果。

### 4.2 账号模式

- Windows 和 Android 使用同一套账号系统。
- 账号第一阶段使用“邮箱 + 密码”作为标识，短信登录和第三方 OAuth 作为后续 provider，不进入当前 MVP。
- 邮箱验证在开发/演示环境可由配置关闭；公开发布前必须开启验证。
- 登录状态必须跨应用重启保持；退出登录必须使当前设备的刷新令牌失效。
- 用户可以查看“我的设备”、查看已授权的配对关系，并随时撤销授权。
- 账号删除必须撤销所有 refresh token、设备登录关系和配对关系；是否删除云端元数据必须二次确认。

### 4.3 账号与远程控制的关系

必须遵守以下顺序：

```text
登录账号
  -> 设备登记
  -> 手机发现同账号电脑
  -> 手机发起控制授权
  -> Windows 本机确认
  -> 建立受控设备关系
  -> 执行低风险或需确认的任务
  -> 写入审计日志
```

规则：

- 同账号设备默认显示为“未授权可控制”。
- 同一账号不会自动继承其他设备的控制权限。
- Windows 本机确认是最终授权边界，Relay 不能代替。
- 解绑后立即撤销对应关系；未完成命令必须明确进入 `rejected` 或 `cancelled`。
- 一台电脑可以授权多台手机的场景暂不开放，Phase 2 先保证一台手机与一台电脑的最小闭环。

## 5. 技术设计

### 5.1 认证与令牌

- 密码只保存为 Argon2id 加盐哈希，绝不明文存储。
- 登录成功后签发：
  - 短期 access token；
  - 可旋转 refresh token。
- 服务端只保存 refresh token 哈希和会话元数据。
- access token 不放入 URL 查询参数；HTTP 使用 `Authorization: Bearer`，WebSocket 使用子协议或首包认证。
- 设备 token 与账号 token 分离：账号 token 解决“用户是谁”，设备 token 解决“这台设备如何接入 Relay”。
- 失败、过期、撤销和账号禁用必须有明确错误码，不允许静默失败。

### 5.2 规划数据表

在现有 `devices`、`pairings` 之上增加或迁移：

- `users`：账号主记录、状态、创建时间；
- `user_credentials`：密码哈希、算法参数、更新时间；
- `auth_sessions`：refresh token 哈希、设备、过期时间和撤销时间；
- `device_enrollments`：账号与设备的归属关系；
- `pairing_requests`：一次性授权请求、过期时间和确认状态；
- `device_pairings`：控制设备、目标设备、权限范围和撤销状态；
- `auth_audit_log`：注册、登录、刷新、退出、撤销和异常登录的元数据。

迁移要求：

- 不破坏现有游客设备；
- 旧设备首次登录时进入绑定流程，而不是自动获得控制权限；
- 现有 Session、Message、Turn 和本地文件不因账号迁移被删除。

### 5.3 规划接口

现有 Relay API 继续保留设备 token 路径。账号层新增：

```text
POST   /v1/auth/register
POST   /v1/auth/login
POST   /v1/auth/refresh
POST   /v1/auth/logout
GET    /v1/auth/me

GET    /v1/account/devices
POST   /v1/account/devices/claim
DELETE /v1/account/devices/{device_id}

POST   /v1/control/pairing-requests
POST   /v1/control/pairing-requests/{id}/approve
POST   /v1/control/pairing-requests/{id}/reject
GET    /v1/control/pairings
DELETE /v1/control/pairings/{pairing_id}
```

最终路径可以在实现时统一，但以下原则不能改变：

- 账号身份与设备控制授权分离；
- 控制关系必须由目标设备确认；
- 任何撤销都必须在服务端立即生效；
- 所有接口都必须有明确错误码和审计记录。

## 6. 权限边界

Phase 2 第一版只允许：

- `device.ping`
- `device.status`
- `file.list`
- `file.read`
- `app.open`（应用白名单）
- `doc.create`（需要本机确认）
- `file.write`（需要本机确认）
- `file.move`（需要本机确认）

永久禁止或默认关闭：

- `shell.run`
- `powershell.run`
- `cmd.run`
- `file.delete`
- 任意 executable + 任意参数
- 无边界递归操作
- 未经确认的系统设置修改

## 7. 验收标准

- 游客不登录即可完成本地对话和本地文件操作。
- 游客访问远程控制入口时看到明确的登录提示，而不是静默失败。
- 同账号电脑和手机登录后，可以在设备列表互相发现。
- “同账号”本身不能让手机获得控制权限。
- 手机发起控制请求后，Windows 必须本机确认；未确认时状态为 `waiting_confirmation`。
- 手机可以撤销授权，Windows 也可以主动撤销。
- 撤销后新命令立即失败，旧命令进入明确终态。
- 登录状态跨应用重启保持；退出登录后 refresh token 失效。
- 密码错误、令牌过期、设备被撤销和账号禁用均返回明确错误码。
- 账号删除后，账号级 token 和配对关系不再可用。
- 所有注册、登录、授权、撤销和远程任务都能在审计日志中还原。

## 8. 明确不在本 ADR 首版范围

- 短信验证码登录；
- 第三方 OAuth/SSO；
- 自动把同账号设备设为互相信任；
- 云端同步完整聊天历史；
- 多电脑、多手机复杂权限矩阵；
- 管理员后台和 RBAC/ABAC；
- 端到端加密协议的最终实现。

## 9. 结果

LocalMind / LocalFile 将采用：

```text
游客模式
  -> 本地能力可用
  -> 无远程协同

账号模式
  -> 同账号登录
  -> 设备登记
  -> 显式设备授权
  -> 目标设备确认
  -> 受控远程任务
```

这一设计允许“任何人下载安装后本地直接使用”，同时把跨设备协同从“账号登录即信任”提升为“账号身份 + 设备授权 + 本机确认 + 审计”的受控通道。
