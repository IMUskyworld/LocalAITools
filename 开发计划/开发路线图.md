## 1. 产品定义

### 1.1 一句话定位

一套可在 Windows 和 Android 之间协同的个人 AI 工具：

- **LocalMind（Windows）**：以桌面 Agent 为核心，理解任务、调用工具、操作文件和生成文档。
- **LocalFile（Android）**：以移动端文件处理和 AI 助手为核心。
- **双端互联（新增目标）**：Android 通过受控通道远程查看和控制 Windows 上的 LocalMind。

### 1.2 产品边界

| 项目 | 当前定位 | 不做什么 |
|---|---|---|
| LocalMind | Windows 桌面 Agent | 不做通用 RPA、不做任意 Shell、不做无人监管的高危操作 |
| LocalFile | Android 文件 AI 助手 + 远程控制入口 | 不把 Windows 的全部系统权限复制到手机 |
| 通信层 | 双端受控命令通道 | 不做公网裸端口、不做匿名控制、不做随意执行命令 |
| Memory | 后续可审计的长期记忆 | 不自动记录隐私内容，不让记忆污染和无限增长 |
| 模型 | 在线模型与本地模型可切换 | 不把模型选择与权限边界绑定在一起 |

### 1.3 核心用户价值

1. 用户可以在 Windows 上通过自然语言完成文件整理、文档生成和应用打开。
2. 用户可以在 Android 上处理文件、生成文档。
3. 用户在手机上可以安全地向已配对的 Windows 设备发送任务。
4. 任务状态、执行过程、失败原因和操作审计在双端可见。
5. 不依赖用户手动开启 PowerShell、命令行或安装 Python 环境。

## 2. 当前代码事实（基线）

### 2.1 当前技术栈

| 端 | 技术栈 | 当前事实 |
|---|---|---|
| LocalMind 前端 | React + TypeScript + Vite | Tauri WebView UI |
| LocalMind 控制面 | Rust + Tauri 2 | IPC、进程管理、文件与设备命令 |
| LocalMind Agent | Python + Pydantic AI 2.x | `localmind/scripts/agent_server.py`，SSE 流式 |
| LocalMind 离线路径 | Ollama | 现有路径不扩展为 Phase 0 主目标 |
| LocalFile | Kotlin + Jetpack Compose | 手写 Agent 循环、Room、文件生成 |
| 共享契约 | `shared-contract` | 当前基本为未接入的死代码，后续再决定去留 |

### 2.2 当前必须认可的问题

- Session、Message、Turn 等数据主要停留在内存，应用重启会丢失。
- 工具调用结果没有完整落盘，跨轮上下文断裂，Agent 会忘记刚做过什么。
- Context 采用全量历史发送，长会话会膨胀、超限或明显劣化。
- Rust、TypeScript、Python 存在多套工具定义和重复职责。
- 部分 Legacy Tauri Command 暴露了高风险能力或已经没有真实调用点。
- `device_id` 不稳定，无法作为可靠的设备身份。
- IPC 存在静默返回 `null` 的错误处理，持久化失败可能被 UI 当成成功。
- 当前没有稳定的 Agent 评测集，无法区分“模型差”和“Harness 差”。
- 双端远程控制没有可交付的当前实现，历史云端中继方案已不符合现状态。

### 2.3 当前明确不得复活的东西

以下内容只能作为历史研究材料；ADR-002 已重新立项 Relay-first，允许实现受约束的语义化公网 WSS Relay：

- 旧 RelayCloud 的三组件实现和公网裸端口。
- new-api 作为当前在线模型网关。
- 未经 ADR-002 约束的任意公网远程控制。
- 任意 Shell / PowerShell 执行工具。
- 无路径边界、无确认、无审计的文件删除或批量写入。
- 为了“全平台”而同时重写 Windows、Android 和共享协议。

## 3. 目标架构原则

### 3.1 分层

```text
┌──────────────────────── Android LocalFile ────────────────────────┐
│ 文件 AI 处理 │ 本地会话 │ 远程任务面板 │ 配对与设备管理 │ 事件日志 │
└──────────────────────────────┬────────────────────────────────────┘
                               │
                     Tailnet / 局域网受控通道
                               │
┌──────────────────────────────▼────────────────────────────────────┐
│                      Windows LocalMind                            │
│                                                                   │
│  React UI                                                         │
│    └─ 只通过类型化 IPC/API 访问控制面，不持有系统权限             │
│                                                                   │
│  Rust Control Plane                                               │
│    ├─ SQLite：Session / Turn / Message / ToolCall / Audit         │
│    ├─ Device ID / Settings / Migration                            │
│    ├─ IPC 错误边界                                                 │
│    ├─ 远程服务、配对、鉴权、命令去重和状态机                      │
│    └─ Tool Policy 的最终执行边界                                   │
│                                                                   │
│  Python Agent Harness                                             │
│    ├─ Pydantic AI Agent Loop                                       │
│    ├─ Context Manager（后续 Phase）                               │
│    ├─ Tool Registry                                                │
│    ├─ Tool Guard                                                    │
│    └─ SSE 事件输出                                                 │
└───────────────────────────────────────────────────────────────────┘
```

### 3.2 职责边界

| 层 | 负责 | 禁止 |
|---|---|---|
| React / Compose | 展示、输入、任务状态、确认 UI | 不自行实现工具执行和权限判断 |
| Rust | 持久化、设备身份、IPC、远程服务、审计 | 不重做 Python Agent Loop |
| Python | Agent Loop、Context、工具注册与执行 | 不绕过 Rust 的持久化和审计边界 |
| SQLite | Session/Turn/Message/ToolCall 的 Source of Truth | 不被 Python 临时缓存替代 |
| Tailnet/传输层 | 加密可达性和设备间传输 | 不承担业务授权，不暴露任意命令接口 |

### 3.3 单一事实来源

- Session、Turn、Message、ToolCall、Attachment：以 SQLite 为准。
- Pydantic AI 原始消息缓存：只能作为 replay cache，不能作为业务 Source of Truth。
- Tool 定义：以 Python Tool Registry 为单一源，导出给 UI 和协议消费。
- 远程命令：以包含 `command_id` 的版本化 Envelope 为准，必须可幂等、可审计、可重放状态。
- 设备身份：首次生成后持久化，后续保持不变。

## 4. 核心领域模型

### 4.1 Session

表示一段独立对话和工作上下文。

必备字段：`id`、`title`、`mode`、`device_id`、`created_at`、`updated_at`、`status`。

### 4.2 Turn

表示一次用户请求对应的完整 Agent 执行周期。

状态机：

```text
pending -> running -> completed
                    -> failed
                    -> cancelled
                    -> interrupted
```

硬约束：

- 同一个 Session 同时最多只能有一个 `running` Turn。
- 由 SQLite 唯一索引强制保证，不能只依赖前端防抖。
- 新建 Turn 失败时必须向 UI 返回明确错误。

### 4.3 Message

表示会话中可见或可回放的消息，至少区分：

- `user`
- `assistant`
- `tool`
- `system`
- `summary`

Message 必须归属于 Session 和 Turn；工具消息必须通过 `tool_call_id` 与 ToolCall 建立关系。

### 4.4 ToolCall

记录每次工具调用的：

- 名称、参数、开始和结束时间；
- 调用来源：本地 UI、Python Agent、远程命令；
- 结果、错误类型、耗时、是否被策略拒绝；
- 与 Turn、Message、Session 的关联。

### 4.5 RemoteCommand

远程命令不是“Shell 字符串”，而是语义化操作。

必备字段：

- `command_id`：幂等标识；
- `protocol_version`；
- `source_device_id`；
- `target_device_id`；
- `session_id` / `turn_id`；
- `action`、`args`、`risk_level`；
- `status`、`seq`、`created_at`、`expires_at`。

状态机：

```text
created -> queued -> delivered -> accepted -> running
                                      -> waiting_confirmation
                                      -> completed
                                      -> failed
                                      -> rejected
                                      -> expired
                                      -> cancelled
```

### 4.6 AuditEvent

任何修改磁盘、应用状态或远程控制行为都必须记录：

- 谁发起；
- 在哪个设备；
- 对什么对象；
- 风险等级；
- 是否经过确认；
- 执行结果和错误；
- 是否可撤销及撤销信息。

## 5. 总体阶段路线图

| 阶段 | 目标 | 是否当前要做 | 退出条件 |
|---|---|---|---|
| Phase 0 | 止血、持久化、最小安全边界 | 是 | 安全、数据、构建和主路径全部验收 |
| Phase 1 | Agent Harness 基线、评测和最小修复 | 已完成 | 已能定量区分模型与 Harness |
| Phase 2 | 双端远程控制 MVP | 否，Phase 1 后 | 手机安全控制 Windows 的低中风险任务闭环 |
| Phase 3 | Context Manager 与长期 Memory | 否，Phase 2 后 | 长会话稳定、记忆可审计可删除 |
| Phase 4 | 发布加固与正式打包 | 否，Phase 3 后 | 可重复构建、安装、升级、回滚 |
| Phase 5 | 清理与扩展 | 否，按需 | 死代码和新功能都有明确依据 |

**顺序原则：** Phase 0 不得跳过；Phase 1 的评测基线是后续性能和双端安全的判据；远程控制依赖 Turn、ToolCall、审计、权限和状态机，不能靠“只做一个 WebSocket”上线。

## 6. Phase 0：止血、持久化与最小边界

### 6.1 目标

1. 修复 installer 路径不一致。
2. 删除危险或无真实调用点的 Legacy Tauri Commands。
3. 修复 IPC 静默失败。
4. 建立 SQLite 持久化与 migration。
5. 完成 Session / Message / Turn / Device ID 落库。
6. 建立最小 Python Tool Registry 与 Tool Guard。
7. 保持现有 Agent 主路径可用。

### 6.2 明确不做

- 不实现 Context Manager。
- 不实现摘要、Token Budget、长期 Memory。
- 不实现 Android 远程控制和 Tailscale。
- 不实现完整 Permission Gateway、Undo 和确认 UI。
- 不重写 `agent_server.py` 的 Pydantic AI Agent Loop。
- 不引入微服务、消息队列、向量数据库、多 Agent、插件系统。
- 不顺手清理所有历史死代码；只清理本阶段经过真实调用点验证的内容。

### 6.3 工作项

#### A. Installer

- 将 `build-installer.ps1` 的暂存路径修正为 `$StageDir\scripts\localmind-agent`。
- 验证 `LocalMindSetupBuild\scripts\localmind-agent\localmind-agent.exe` 存在。
- 验证 NSIS 不再出现 `File not found`。

#### B. Legacy Commands

在确认真实调用点后：

- 删除 `run_command`。
- 删除 `delete_path`。
- 删除 `rename_path`。
- 删除 `append_file`。
- 删除 `ollama_chat` IPC。
- 对 `write_file`、`read_file`、`list_dir`、`create_doc` 的 Rust 实现：无真实调用点则删除。
- 保留 `open_app`、`get_common_paths`、`check_ollama`、`files::read_text_file`。
- 不得误删 Python Agent 中的同名工具。
- 不得误删 Rust 内部启动 Python Agent 和 `make_doc.exe` 的进程调用。

#### C. IPC 错误边界

- 禁止 `catch(error) { return null; }` 这类静默吞错。
- 引入显式 `IpcError`，至少包含 `command`、`code`、`message`。
- Session、Message、Turn、SQLite 写失败必须显式失败。
- 禁止数据库失败后生成 fake ID 并继续假装成功。

#### D. SQLite 与 Migration

- 依赖：`rusqlite = { version = "0.32", features = ["bundled"] }`。
- 数据库：`%APPDATA%\LocalMind\localmind.db`。
- PRAGMA：`foreign_keys=ON`、`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`。
- migration 使用 `PRAGMA user_version`。
- 建立表：`sessions`、`turns`、`messages`、`tool_calls`、`attachments`、`session_summaries`、`app_settings`、`audit_log`、`memory_entries`。
- Phase 0 只读写 `sessions`、`turns`、`messages`、`app_settings`；其余表只建 schema。
- migration 前使用 SQLite backup API 创建 `localmind.db.bak.vN`。
- 禁止 destructive migration，禁止数据库异常时自动删除数据库。

#### E. Session 与 Turn

- Session：create、list、rename、delete。
- Message：list、create。
- Turn：begin、complete、fail/cancel/interrupted。
- 删除 Session 时级联删除 messages、turns、tool_calls、attachments、session_summaries。
- 唯一索引保证同一 Session 最多一个 running Turn。
- 正式 UI 不再依赖旧 `append_message` / `send_message` mock 作为主路径。

#### F. Device ID

- 首次生成并写入 `app_settings`。
- 后续重复读取必须返回同一个 ID。
- 不允许每次调用生成新 UUID。

#### G. Python Tool Registry 与 Tool Guard

新增或整理：

- `localmind/scripts/tool_registry.py`
- `localmind/scripts/tool_policy.py`

Registry 至少记录：

- `name`
- `description`
- `risk_level`
- `path_policy`
- `timeout_ms`
- `max_output_chars`
- `cacheable`
- `enabled`

Tool Guard 至少实现：

- `canonicalize_path()`
- `is_within_allowed_roots()`
- `validate_open_target()`

默认 roots：

- `%USERPROFILE%\Desktop`
- `%USERPROFILE%\Documents`
- `%USERPROFILE%\Downloads`
- `%USERPROFILE%\OneDrive\Desktop`
- `%USERPROFILE%\OneDrive\Documents`

额外例外：

- `%USERPROFILE%\.ollama\models` 只允许打开，不允许写、移动、生成文档。

必须拒绝：

- 路径穿越 `..`
- `C:\Windows`
- `C:\Program Files`
- UNC 路径
- `\\?\` 和 device namespace
- roots 外的写入、移动和文档生成

## 7. Phase 1：Harness 基线、评测与最小修复

### 7.1 目标

先测量，再优化。目标是回答：

> Agent 表现差，究竟来自模型、上下文、Prompt、工具定义，还是 Agent Loop？

### 7.2 必须建立的内容

#### A. 固定评测集

至少 12 条，后续扩展到 30 条，覆盖：

- 单工具调用；
- 多工具串联；
- 跨轮记忆；
- 长会话第 1 轮信息回忆；
- 工具报错后自我修正；
- 路径错误；
- 文档生成；
- 安全拒绝；
- 重复调用检测；
- 取消任务；
- 时间/Token 预算；
- 远程任务的模拟执行。

每条任务记录：

- 是否成功；
- 使用了哪些工具；
- 工具调用次数和轮次；
- 是否重复调用；
- 输入/输出 token；
- 首 token 延迟和总耗时；
- 是否越权；
- 错误恢复结果。

#### B. 结构化 Trace

每个 Turn 输出一条可持久化 Trace：

```text
turn_started
context_built
model_request_started
model_response_received
tool_call_started
tool_call_finished
retry_started
turn_completed / turn_failed / turn_cancelled
```

### 7.3 允许的 Harness 修复

- System Prompt 明确角色、工具规则、停止条件和拒绝规则。
- Tool Schema 统一、精简、类型化，并增加失败语义。
- Agent Loop 增加最大步骤数、单工具超时、取消检查和单 Turn 重复调用检测。
- 工具错误统一为结构化错误，不能把异常字符串原样塞回模型。
- 记录模型、工具、上下文和 token 统计。
- 对同一模型做改造前后 A/B 对比。

### 7.4 不在本阶段做

- 不自动引入长期记忆。
- 不重写 Pydantic AI Agent Loop。
- 不实现复杂多 Agent 编排。
- 不把评测分数当作真实验收的替代品。

### 7.5 退出标准

- 12 条核心评测任务可以重复运行。

## 8. Phase 2：双端远程控制 MVP

### 8.1 前置依赖

必须完成 Phase 0 和 Phase 1。没有 Turn、ToolCall、审计、权限和稳定评测，不进入远程控制。

### 8.2 传输方案

Phase 2 第一版固定为 **Relay-first**，依据是 `ADR-002-relay-first.md`：

```text
Android LocalFile
        │  WSS（仅出站）
        ▼
LocalMind Relay（公网 TLS）
        ▲  WSS（仅出站）
        │
Windows LocalMind Remote Service
```

原则：

- Windows 不监听公网控制端口，Android 与 Windows 均只建立出站 WSS。
- Relay 必须使用 TLS；公网明文 HTTP 只能用于本机健康检查或临时重定向。
- 应用层必须做设备 token、配对关系、命令白名单、幂等和状态机校验。
- Relay 只转发版本化 Envelope，不执行命令、不保存 DeepSeek Key、不持久化明文文件内容。
- 离线命令进入持久队列，设备重连后按序补发；重复 `command_id` 不得重复执行。
- Tailscale/局域网直连降级为开发、高级用户和故障排查通道，不是普通用户必经步骤。
- 在文件内容通过 Relay 传输前，必须完成客户端端到端加密；Relay 只处理 opaque payload。

### 8.3 账户模式与游客模式

该决策由 `开发计划/ADR-003-account-and-guest-mode.md` 固化，Phase 2 实现时不得把账号身份与设备控制授权混为一谈。

#### 8.3.1 两种使用模式

- **游客模式**：无需注册、无需密码，本地 AI 对话、本地文件处理、本地 Agent 和本地文档生成正常可用；账号设备列表、跨端同步和远程控制入口默认禁用。
- **账号模式**：Windows 和 Android 使用同一套账号系统登录。账号用于识别用户、登记设备和查看“我的设备”，不自动授予远程控制权限。
- 游客升级账号时保留本地 Session、Message、Turn 和文件；默认不上传聊天记录、文件正文或工具结果。
- 游客点击协同入口时必须给出明确的“登录后使用”提示，不能静默失败。

#### 8.3.2 账号与设备的关系

```text
同一账号
  -> 识别用户
  -> 登记设备
  -> 展示“我的设备”
  -> 发起控制授权请求
  -> 目标设备本机确认
  -> 建立受控设备关系
```

- 同一账号只证明设备属于同一用户，不等于手机可以控制电脑。
- 同一账号下的设备默认显示为“未授权可控制”。
- 远程控制必须经过设备授权、目标设备确认、本机权限检查和审计。
- 账号、设备 token、控制配对关系必须分开存储、分开撤销。

#### 8.3.3 认证与账户 MVP

- 第一阶段使用“邮箱 + 密码”注册登录；短信登录、第三方 OAuth/SSO 不作为当前 MVP 前置。
- 密码使用 Argon2id 加盐哈希，服务端不保存明文密码。
- 使用短期 access token + 可旋转 refresh token；refresh token 只保存哈希。
- 设备 token 与账号 token 分离；退出账号必须使当前设备的 refresh token 失效。
- 支持查看设备、撤销设备、查看和撤销控制配对、注销账号。
- 邮箱验证在开发/演示环境可通过配置关闭；公开发布前必须开启。

#### 8.3.4 规划的账号接口与数据

账号接口至少包括：

```text
POST   /v1/auth/register
POST   /v1/auth/login
POST   /v1/auth/refresh
POST   /v1/auth/logout
GET    /v1/auth/me
GET    /v1/account/devices
POST   /v1/account/devices/claim
DELETE /v1/account/devices/{device_id}
```

规划数据表：

```text
users
user_credentials
auth_sessions
device_enrollments
pairing_requests
device_pairings
auth_audit_log
```

现有 `devices`、`pairings` 和 Relay WSS 协议保留兼容；账号层是在设备身份之上增加用户身份和控制授权，不是替换现有 Relay。

#### 8.3.5 安全边界

- access token 不放入 URL 查询参数；HTTP 使用 `Authorization: Bearer`，WebSocket 使用子协议或首包认证。
- 密码错误、账号禁用、token 过期、设备撤销和配对拒绝必须有明确错误码。
- 账号被盗不能直接获得远程控制权，仍需要目标设备确认。
- 解绑、撤销或注销后，新命令立即失败，未完成命令进入 `rejected` 或 `cancelled`。
- 新账号系统不得改变 Relay 的永久安全红线，不得增加任意 Shell、PowerShell、CMD 或任意 executable 能力。

### 8.4 配对与设备授权

- Windows 首次启动生成持久化 `device_id` 和设备密钥。
- 手机通过二维码或短配对码获取设备信息。
- 配对码一次有效并设置过期时间。
- 手机在同一账号下发现电脑后，只能发起授权请求，不能直接执行控制命令。
- Windows 本机显示请求来源、权限范围和有效期，用户确认后才保存设备凭证。
- 每个设备有独立凭证，不共享“全局万能 key”。
- 任一端都可以发起解绑；目标设备撤销后立即失效。
- 所有远程命令携带 `command_id`、`seq` 和时间戳，防止重放。

### 8.5 远程命令边界

第一版允许的低风险命令：

- `device.ping`
- `device.status`
- `file.list`
- `file.read`
- `app.open`（应用白名单）
- `doc.create`（需要本机确认）
- `file.write`（需要本机确认）
- `file.move`（需要本机确认）

永久禁止或默认关闭：

- `shell.run`
- `powershell.run`
- `cmd.run`
- `file.delete`
- 任意 executable + 任意参数
- 无边界递归操作
- 未经确认的系统设置修改

如果未来要开放更高风险能力，必须完成 Phase 3 的完整 Permission Gateway，并提供双重确认、备份、审计和 Undo。

### 8.6 远程任务流程

```text
手机创建 command
    -> Windows 接收并校验设备、权限和幂等
    -> 创建或关联 Turn
    -> 风险检查
    -> 低风险直接执行
    -> 中风险 waiting_confirmation
    -> Windows UI 确认
    -> 执行并持续发送 progress 事件
    -> completed / failed / rejected
    -> 双端保存结果和审计
```

### 8.7 验收标准

- 游客不登录即可完成本地对话和本地文件操作，远程协同入口有明确登录提示。
- 同账号设备登录后可以互相发现，但同账号本身不能获得控制权限。
- 手机发起控制请求后，Windows 必须本机确认；未确认时状态为 `waiting_confirmation`。
- 10 次配对尝试至少成功 9 次。
- 已配对设备之间建立连接不超过 60 秒。
- 低风险远程命令的传输时延 P95 ≤ 3 秒，不含模型生成耗时。
- 电脑离线、超时、关机、权限拒绝和重复 `command_id` 均有明确状态。
- 手机界面显示 `sent / delivered / running / waiting_confirmation / completed / failed`。
- 手机断线重连后能补齐未确认状态。
- 撤销授权后新命令立即失败，未完成命令进入 `rejected` 或 `cancelled`。
- 不存在公网裸端口。
- 远程任务可在审计日志中完整还原。
- 手机端不能通过伪造 action 调用未注册能力。

## 9. Phase 3：Context Manager 与长期 Memory

### 9.1 Context Manager

目标：长会话稳定、信息不丢、Token 不无限增长。

原则：

- tool call 和 tool result 必须成对保留或成对丢弃。
- 固定部分优先保留：System Prompt、工具 schema、当前用户输入。
- 最近消息优先保留。
- 早期内容超过预算时才摘要。
- 摘要缓存到 `session_summaries`，避免每轮重复生成。
- 上下文预算不得超过模型安全上限，默认保留余量。
- 任何压缩都不得改变 Turn 的审计记录。

### 9.2 Memory

三层：

1. 当前 Turn 工作记忆。
2. 当前 Session 会话摘要。
3. 跨 Session 长期记忆。

长期记忆硬规则：

- 来源可追溯。
- 有置信度和更新时间。
- 用户可查看、编辑、删除和导出。
- 不自动记录密码、密钥、证件号、聊天隐私等敏感信息。
- 不因为一次闲聊就写入长期记忆。
- 记忆冲突时保留来源，不静默覆盖。
- 检索必须有 Token 上限。

### 9.3 验收标准

- 20 轮以上会话仍能正确引用第 1 轮关键事实。
- Long context 不出现无限增长。
- 工具调用历史可回放。
- 新会话可检索到经过确认的长期记忆。
- 删除记忆后不再被检索。
- 摘要和记忆污染有回归测试。

## 12. 关键接口与错误契约

### 12.1 IPC

```ts
type IpcError = {
  command: string
  code: string
  message: string
  cause?: unknown
}
```

原则：

- 不允许用 `null` 表示失败。
- 不允许吞掉数据库错误、权限错误和命令不存在错误。
- 调用方必须能够区分 `not_found`、`policy_denied`、`conflict`、`timeout`、`internal`。

### 12.2 Turn API

```text
turn_begin(session_id, user_input, attachments?) -> turn_id
turn_complete(turn_id, assistant_message) -> void
turn_fail(turn_id, code, message, retryable) -> void
turn_cancel(turn_id) -> void
```

### 12.3 Tool Registry

每个工具至少声明：

```json
{
  "name": "read_file",
  "description": "读取允许根目录内的文本文件",
  "risk_level": "L0",
  "path_policy": "allowed_roots_read",
  "timeout_ms": 10000,
  "max_output_chars": 12000,
  "cacheable": true,
  "enabled": true
}
```

### 12.4 Remote Envelope

```json
{
  "protocol_version": "1.0",
  "command_id": "uuid",
  "seq": 1,
  "source_device_id": "uuid",
  "target_device_id": "uuid",
  "action": "file.read",
  "args": {},
  "created_at": "ISO-8601",
  "expires_at": "ISO-8601"
}
```

任何不认识的 action、版本不兼容、重复 `command_id`、过期命令、越权参数都必须在执行前拒绝。

## 13. 安全等级

| 等级 | 示例 | 本地策略 | 远程策略 |
|---|---|---|---|
| L0 只读 | read_file、list_dir、read_clipboard | 可在 roots 内自动执行 | 可查看，需设备认证 |
| L1 低风险 | open_app 白名单、生成非敏感文档 | 自动执行 | 本机确认后执行 |
| L2 修改 | write、move、批量整理 | 需要明确目标 | 必须本机确认 |
| L3 高危 | delete、系统设置、命令执行 | Phase 0-3 禁止 | 禁止 |
| L4 任意命令 | PowerShell / cmd / executable | 永久禁止通过 Agent 暴露 | 永久禁止 |

安全红线：

- 不把 Tool Guard 放在 UI 层。
- 不把路径合法性判断放在模型 Prompt 里。
- 不依赖“模型不会乱来”作为安全设计。
- 不做全局 `(tool_name + args_hash)` 永久去重，避免把合法重复操作误判为重复调用。
- 只在明确可缓存的只读工具和当前 Turn 内做重复识别。

## 17. Phase 0 已确认决策

以下决策已确认并已落到 Phase 0 实现中：

1. 接受 `turn_begin / turn_complete / turn_fail` 取代正式 UI 对 `append_message / send_message` 的依赖。

## 附录 A：产品优先级结论

- 双端互联是产品差异化方向，但不能先于基础设施和权限边界。
- 推荐顺序是：**Phase 0 → Harness 基线 → 双端远程 MVP → Context/Memory → 发布加固**。
- 如果因课程演示需要提前展示双端效果，可以做“只读、强确认、受审计”的远程 MVP，但不能绕过 Phase 0。
- Relay-first 是当前默认实现路径；`tsnet`/Tailscale 只保留为高级或降级方案。
- Agent 智商问题先通过评测定位，再做 Context、Prompt、Tool 和 Loop 的系统优化，不通过盲目换模型解决。
